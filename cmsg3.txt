fix(a11y,security): stop leaking the DB secret, fix 8 tap targets

**The Content DB and Security DB secrets were being written to the build
log.** I found this by reading the output of a build rather than trusting
it was green:

    [contentbase] Falling back to seed for "settings": Error: Dynamic server
    usage: Route /sitemap.xml ... fetch https://script.google.com/.../exec
    ?secret=mike201422

The Apps Script read path authenticates with `?secret=` in the query
string — that is the contract the deployed `.gs` expects, so it cannot
just move to a header. But **Next.js embeds the entire fetch URL, query
string included, in its own `DYNAMIC_SERVER_USAGE` error description**,
and both store layers logged that error object verbatim on every seed
fallback. So the secrets landed in stdout, which means the Vercel build
log, which means anyone who can read build output could rewrite every
listing and every admin credential.

`lib/store/redact.ts` scrubs them in three passes: the configured values,
then a catch-all for anything still shaped like `?secret=…` or
`"secret":"…"` (which catches a rotated value still sitting in a stale
env file), then a depth-capped, cycle-safe walk for bare objects —
`fetch` rejections throw those, and a pass-through there would have been
a second hole. 16 tests, including one that caught the bare-object hole
in the first version.

⛔ **The secret itself should still be rotated** — it was in the log for
as long as that build ran. That needs the owner's Vercel + Google access.

Also fixed, all found by `scripts/qa-audit.mjs` at 360px against the live
site: eight interactive elements under the WCAG 2.2 AA 24×24 floor
(2.5.8) — four footer legal links at 16px tall, three "read more" links
at 20px, and the consent checkbox at 16×16. The footer uses `-m-2 p-2`
so the hit area grows to 24px while the visual spacing is unchanged.

That script is the real addition: Playwright + axe-core against the live
deployment, checking horizontal overflow, target size, console errors,
failed requests, and axe violations across 360/768/1024/1440. Horizontal
overflow came back **0/32**, which no amount of reading the CSS could
have told us. ⚠️ Only the 360px pass completed — the rest hit
`ERR_INTERNET_DISCONNECTED` on this machine — so **axe-core has not run
yet**, and the tap-target fixes are unverified until Vercel deploys them.
